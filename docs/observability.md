# Мониторинг и журнал действий

Суперадминистратор открывает **Мониторинг** в меню или `https://APP_DOMAIN/metrics`.
После существующего входа приложение выдаёт отдельную защищённую cookie на 8 часов.
Grafana открывается без второго пароля. Для каждого запроса Caddy проверяет актуальную
роль в базе; снятие роли и удаление аккаунта закрывают доступ. Выход из приложения
удаляет cookie. Истёкшая сессия возвращает на страницу входа в мониторинг.

Dashboard **Нагрузка** показывает RPS, статусы, задержки p50/p95/p99, активные запросы,
CPU, память, GC и потери логов. **Технические логи** показывает привычные события
Serilog, включая доступные старые файлы. **Действия администраторов** показывает
изменения «было → стало», сотрудника, роль, объект и результат; RequestId ведёт к
связанным техническим событиям. Выдача ограничена 1000 событиями на запрос — для
длинной истории сузьте период и фильтры.

## Настройки и хранение

В `.env` рядом с Compose добавьте четыре **разных** случайных значения:

```dotenv
MONITORING_PROXY_KEY=...
METRICS_SCRAPE_KEY=...
GRAFANA_BOOTSTRAP_PASSWORD=...
GRAFANA_SECRET_KEY=...

# Необязательно: значения по умолчанию.
METRICS_RETENTION=30d
TECHNICAL_LOG_RETENTION=336h
ADMIN_AUDIT_RETENTION=8760h
LOG_IMPORT_LIMIT_BYTES=1073741824
```

Для каждого секрета подходит результат `openssl rand -hex 32`. Пароль Grafana
используется только при первоначальном создании её внутреннего администратора;
пользователи сайта получают роль **Viewer** через Auth Proxy. Внешний парольный вход,
анонимный вход и Grafana Live выключены. Dashboard и источники данных поставляются
из репозитория, поэтому изменения в них выполняются в конфигурации.

В Compose мониторинг включён через `Monitoring__Enabled=true`; без Compose он
по умолчанию выключен. Prometheus читает защищённый `/internal/metrics` API и
диагностику Alloy/Loki каждые 15 секунд. RPS вычисляется за минуту; исключены
статика, health-check и мониторинг. ID и конкретные URL не используются как метки.

| Данные | Постоянный том | Хранение / ограничение |
|---|---|---|
| Метрики | `prometheus-data` | 30 дней или 5 GB, что наступит раньше |
| Технические логи и аудит в Loki | `loki-data` | 14 дней / 365 дней; очистка Compactor с задержкой до 2 часов |
| Локальные файлы API | `app-logs` | Текст: до 32 файлов по 64 MiB; аудит: до 128 файлов по 16 MiB и 14 дней |
| Импортные снимки | `app-logs/import` | До 1 GiB; отдельная ручная очистка после окна хранения |
| Позиции чтения | `alloy-data` | Checkpoint для каждого файла; не удалять при обновлении |
| Настройки Grafana | `grafana-data` | Сохраняются между перезапусками |

Сроки Loki задаются в **целых часах**, минимум 24 часа. Одинаковое значение
`TECHNICAL_LOG_RETENTION` применяется к возрасту импортируемых событий и их хранению.
Для изменения сроков перезапустите Loki и Alloy. Уже удалённые данные восстановить
увеличением срока нельзя. Временное окно запроса Grafana задаётся отдельно справа
сверху; часы показываются в часовом поясе браузера.

Резервные копии PostgreSQL не содержат Loki, Prometheus и файловых логов. Для их
сохранения отдельно копируйте соответствующие тома после остановки их владельца.
В каталоге Loki нет лимита общего размера: 365 дней аудита требуют расчёта ёмкости
диска по реальной частоте событий. Для мониторинга предусмотрены ограничения CPU
и памяти; вместе с API/БД рекомендуется хост от 8 GiB RAM. Следите за свободным
местом на файловой системе Docker, особенно при первоначальном импорте.

## Первый запуск на работающем сервере

Старый File sink использовал `../logs/server-log-.txt`. При рабочем каталоге
`/app` это **`/logs`**, который раньше не был постоянным томом. Пересоздание старого
API без предварительной копии может потерять его историю. Оригиналы никогда не
удаляются импортом. Не выполняйте `docker compose down -v`.

1. Обновите checkout, заполните новые переменные `.env`, соберите новый образ
   `docker compose build funandchecks-api`. Ошибка сборки не затрагивает работающий API.
2. Остановите **старый** API, сохранив контейнер: `docker stop funandchecks-api`.
   Это обеспечивает полный последний лог, включая многострочные исключения.
3. Скопируйте закрытый снимок до пересоздания контейнера (каталог должен быть новым):

```bash
sh monitoring/snapshot-existing-logs.sh ./log-snapshot-20261014
```

В Windows PowerShell альтернативный помощник:

```powershell
./monitoring/snapshot-existing-logs.ps1 -Destination ./log-snapshot-20261014
```

Если API работал из IDE, остановите его, найдите текстовые файлы в `./logs` проекта
или `../logs` относительно каталога запуска. Скопируйте их в новый снимок. В
PowerShell можно использовать `-Container '' -SourceDirectory <каталог>`; помощник
не изменяет исходники. Снимки могут содержать приватные сведения — храните их закрыто.

4. Убедитесь, что снимок содержит `server-log-*.txt`. Подготовьте права томов и
   импортируйте файлы, передав **абсолютный** путь снимка:

```bash
docker compose run --rm app-volume-init
LOG_IMPORT_DIRECTORY="$(pwd)/log-snapshot-20261014" docker compose --profile tools run --rm --no-deps log-import
docker compose up -d
```

В PowerShell перед импортом задайте
`$env:LOG_IMPORT_DIRECTORY = (Resolve-Path ./log-snapshot-20261014).Path`, затем
выполните ту же команду `docker compose --profile tools run --rm --no-deps log-import`.

Помощник читает снимок только для чтения, проверяет общий лимит импортного каталога,
именует файлы по SHA-256 содержимого и публикует их атомарным переименованием.
Повторный импорт **того же закрытого снимка** не дублирует файлы. Не снимайте ещё одну
копию уже импортированного, продолжающего расти файла: совпадающие записи окажутся
в разных потоках. Проверяйте выходной код помощника: при достижении лимита часть
файлов может уже быть скопирована, остальные остаются в исходном снимке.

5. Войдите суперадминистратором, откройте `/metrics`, выберите последние 14 дней и
   фильтр «Источник: import» в техническом dashboard. Проверьте исходные даты и
   несколько исключений. Сохраните исходный снимок до успешной проверки.

Если запуск новой версии не удался, старый контейнер до пересоздания можно снова
запустить через `docker start funandchecks-api`. После пересоздания используйте
сохранённый старый образ и снимок; обычный откат API не удаляет мониторинговые тома.

После того как импортные записи вышли из окна хранения, удалите только их копии:

```bash
docker compose --profile tools run --rm --no-deps log-import-cleanup
```

Очистка рассматривает только `/app/logs/import/server-log-*.txt`, учитывает время
последнего изменения **и** возраст импортной копии, добавляет час запаса. Исходные
снимки и текущие файлы API не затрагиваются.

## Сбор файлов и отказоустойчивость

Alloy читает один текстовый поток Serilog `/app/logs/server-log-*.txt` и закрытые
импортные снимки. Заголовок содержит миллисекунды и явный часовой пояс; исключения
объединяются до следующего заголовка. Исходное время сохраняется. Записи старше
окна хранения, нераспознанные даты и события больше 256 KB отбрасываются со
счётчиком причины. Полный текст сохраняется с маскированием распознанных токенов,
паролей и кодов. Новые записи содержат RequestId; у старых он может отсутствовать.
История «было → стало» для старых событий не восстанавливается.

Аудит пишется в отдельные `admin-audit-*.jsonl` и не попадает в технический поток.
ФИО и роль сотрудника сохраняются на момент события. Это журнал наблюдаемости:
ограниченная очередь и сбои диска не блокируют операции, поэтому возможны потери.
Готовые записи Alloy отправляет с ограниченными повторными попытками; его позиции
чтения сохраняются, но без экспериментального WAL последняя партия может потеряться
при аварии или продолжительном отсутствии Loki. Это не журнал с гарантией доставки.

Grafana, Loki, Prometheus и Alloy не публикуют наружу порты; они используют закрытую
сеть `monitoring_net`. Caddy удаляет присланные клиентом заголовки идентификации и
передаёт Grafana только проверенный ID. Внешние `/internal` и `/internal/*` возвращают
404. Все постоянные службы запускаются без root; `app-volume-init` — разовый процесс
без сети для подготовки прав. Не открывайте порты мониторинга при диагностике.

## Проверка и диагностика

```bash
# Не печатает подставленные секреты.
docker compose config --quiet
docker compose exec caddy caddy validate --config /etc/caddy/Caddyfile
docker compose exec alloy alloy validate /etc/alloy/config.alloy
docker compose exec prometheus promtool check config /prometheus/config.yml
docker compose logs --tail=100 funandchecks-api alloy loki prometheus grafana caddy
```

Первый запрос `https://APP_DOMAIN/internal/metrics` должен вернуть 404 даже
суперадминистратору. Гость и обычный администратор не должны открывать содержимое
Grafana через прямую ссылку. После снятия роли суперадмина открытая вкладка теряет
доступ при следующем запросе. После выдачи/отзыва награды или изменения оценки
проверьте новую строку в журнале и переход по RequestId.

На dashboard нагрузки доступны `up`, потери очереди API, отклонения парсера Alloy,
не доставленные в Loki события и отклонения Loki. При `up=0` проверьте ключ сборщика,
сетевые адреса и готовность сервиса. При `permission denied` выполните
`docker compose run --rm app-volume-init`. При `too old` проверьте срок импорта и
исходную дату; при `out of order` сохраните имена файлов и метки источника, не
сбрасывайте позиции чтения Alloy. Утрата `alloy-data` может привести к повторному
чтению оставшихся файлов; менять путь или переименовывать импортные файлы не нужно.

Конфигурации проверены официальными валидаторами Caddy, Alloy, Loki и promtool,
также проверены Compose и синтаксис скриптов. Два самостоятельных теста проверяют
реальный прокси и обработку временных логов без Docker:

```bash
node monitoring/tests/verify-caddy.mjs /path/to/caddy
node monitoring/tests/verify-alloy.mjs /path/to/alloy
```

Тесты используют временные каталоги, локальные порты и заглушки, затем завершают
свои процессы. Проверяют запрет внутренних URL и поддельных заголовков, закрытие
доступа при недоступности проверки роли, cookie/redirect, многострочные события,
маскирование, исходный часовой пояс, отбрасывание старых/ошибочных дат и аудит.
Linux Docker daemon в рабочей среде недоступен, поэтому полный запуск контейнеров
и отрисовку dashboard необходимо проверить при первом развёртывании.
